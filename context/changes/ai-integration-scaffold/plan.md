# AI Integration Scaffold Implementation Plan

## Overview

Wire `@anthropic-ai/sdk` into the Astro 6 / Cloudflare Workers project and expose `POST /api/ai/scope` — the first JSON endpoint in the project — that accepts a client inquiry text and returns a structured `{ items: QuoteItem[] }` response generated by Claude Haiku using Zod-validated structured output.

## Current State Analysis

All auth API routes (`src/pages/api/auth/`) redirect on error and return no JSON. `context.locals.user` is set by middleware for every request but `/api/*` paths are not in `PROTECTED_ROUTES`, so auth checks must be done manually inside each endpoint. `src/lib/supabase.ts` establishes the factory pattern to follow: import from `astro:env/server`, return `null` if env missing, no throws.

`QuoteItem` (`{ task: string; hours: number; rate: number }`) already exists at `src/types.ts:3-7` — it matches the structured output schema exactly. `wrangler.jsonc` already has `nodejs_compat_v2` — no changes needed there.

Neither `@anthropic-ai/sdk` nor `zod` is installed.

### Key Discoveries:

- `src/types.ts:3-7` — `QuoteItem` is the response element; reuse, do not define a new type
- `src/lib/supabase.ts:5-7` — factory pattern with graceful null; copy verbatim for `anthropic.ts`
- `src/middleware.ts:4` — `PROTECTED_ROUTES` covers only pages; `/api/ai/scope` needs a manual 401 guard
- `astro.config.mjs:17-20` — existing `env.schema` with two `optional: true` secrets; add `ANTHROPIC_KEY` in the same style
- `wrangler.jsonc` — `nodejs_compat_v2` already present; no changes needed

## Desired End State

`POST /api/ai/scope` is reachable under `npm run dev` (workerd runtime). An authenticated request with `{"inquiry_text": "..."}` returns `HTTP 200` with `{"items": [{task, hours, rate}, ...]}`. An unauthenticated request returns 401. An empty or nonsensical brief returns 422 with `{"error": "inquiry_too_short"}`. The Cloudflare environment picks up `ANTHROPIC_KEY` from `.dev.vars` locally and from `wrangler secret` in production.

## What We're NOT Doing

- No streaming responses — single `messages.parse()` call returning complete JSON
- No rate limiting — MVP scale doesn't warrant it; add at S-01 or later if needed
- No user-editable system prompt context — hardcoded for now; a future slice (see Parked below) will allow users to set their domain/role context
- No changes to `wrangler.jsonc` — `nodejs_compat_v2` already covers the SDK's Node.js polyfill needs
- No CI secret — `ANTHROPIC_KEY` is `optional: true` so builds succeed without it

## Implementation Approach

Three sequential phases: install the two missing packages and wire the env var; create the `anthropic.ts` factory following the established `supabase.ts` pattern; write the scope endpoint introducing the JSON response convention and the `zodOutputFormat()` structured output call.

## Critical Implementation Details

**`zodOutputFormat` import path**: The helper lives at `@anthropic-ai/sdk/helpers/zod`, not the root package — import accordingly: `import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod"`.

**`messages.parse()` availability**: `parse()` is on `client.messages`, not `client.beta.messages` as in older SDK versions. The call signature is `client.messages.parse({ ..., output_config: { format: zodOutputFormat(schema) } })`.

**`parsed_output` may be `null`**: When Claude cannot produce valid structured output, `message.parsed_output` is `null` (not an empty object). The sparse guard must check `parsed_output?.items.length === 0` with the null-coalescing fallback: `const items = message.parsed_output?.items ?? []`.

## Phase 3: Scope Endpoint

### Overview

Create `POST /api/ai/scope` — the first JSON endpoint in the project. It applies a manual 401 auth guard, validates the request body with Zod, calls Claude Haiku via `messages.parse()` with `zodOutputFormat`, applies a 422 sparse guard on empty items, and returns `{ items: QuoteItem[] }`.

### Changes Required:

#### 1. Create the scope endpoint

**File**: `src/pages/api/ai/scope.ts`

**Intent**: Implement the POST handler that orchestrates auth checking, input validation, Claude invocation, and structured response. This file introduces the JSON response pattern and `zodOutputFormat` usage for the first time in the project.

**Contract**:

Export a single `POST: APIRoute`. The handler executes in this order:

1. `if (!context.locals.user)` → `Response({ error: "Unauthorized" }, 401)`
2. `createAnthropicClient()` → if null, `Response({ error: "AI unavailable" }, 503)`
3. `await context.request.json()` → `InputSchema.safeParse(body)` → if invalid, `Response({ error: ... }, 400)`
4. `client.messages.parse()` call — the non-obvious piece:

```typescript
import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";

const message = await client.messages.parse({
  model: "claude-haiku-4-5-20251001",
  max_tokens: 1024,
  system: SYSTEM_PROMPT,
  messages: [{ role: "user", content: inquiry_text }],
  output_config: { format: zodOutputFormat(LineItemsSchema) },
});
```

5. `const items = message.parsed_output?.items ?? []` → if `items.length === 0`, `Response({ error: "inquiry_too_short" }, 422)`
6. `Response({ items }, 200)` — all responses include `Content-Type: application/json`

All `Response` calls use `new Response(JSON.stringify({...}), { status: N, headers: { "Content-Type": "application/json" } })`.

#### 2. Define Zod schemas (same file)

**File**: `src/pages/api/ai/scope.ts` (module-level constants)

**Intent**: `InputSchema` validates the request body; `LineItemsSchema` is the structured output contract passed to `zodOutputFormat`.

**Contract**:
```typescript
const InputSchema = z.object({
  inquiry_text: z.string().min(20),
});

const LineItemsSchema = z.object({
  items: z.array(z.object({
    task:  z.string(),
    hours: z.number(),
    rate:  z.number(),
  })),
});
```
`LineItemsSchema.items` maps directly to `QuoteItem[]` — no type casting needed.

#### 3. Define system prompt (same file)

**File**: `src/pages/api/ai/scope.ts` (module-level constant `SYSTEM_PROMPT`)

**Intent**: Give Claude the domain context needed to produce realistic line items for the Polish freelance market. This is hardcoded for the scaffold; user-editable context is a future slice.

**Contract**: A `const SYSTEM_PROMPT = \`...\`` string that includes:
- Role framing: pricing assistant for a junior freelancer on the Polish market
- Rate anchors by task type (PLN/h ranges): UI/UX design ~80-100, frontend dev ~90-130, backend dev ~100-150, API integration ~100-130, DevOps/deployment ~120-150, project management ~80-100
- Output instruction: decompose into 3-10 concrete deliverables; be conservative on hours; use integer or `.5` steps for hours
- Fallback instruction: if the inquiry is too vague to estimate, return an empty `items` array

### Success Criteria:

#### Automated Verification:

- `npm run lint` passes on the new file (ESLint + TypeScript type-check)
- `npm run build` produces no type errors

#### Manual Verification:

- `npm run dev` starts without errors
- `curl -X POST http://localhost:4321/api/ai/scope -H "Content-Type: application/json" -d '{"inquiry_text": "..."}' -b "session=..."` without auth cookie → 401
- Same request with valid auth session and a real inquiry text → 200 + `{ items: [...] }` with at least 3 items
- Request with `{"inquiry_text": "hi"}` (under 20 chars) → 400
- Request with a genuinely nonsensical brief → 422 + `{ error: "inquiry_too_short" }`

## Testing Strategy

### Manual Testing Steps:

1. Start dev server: `npm run dev`
2. Sign in via the app UI to get an auth cookie
3. Use curl or a REST client (e.g. Bruno, Insomnia) with the session cookie
4. Test 401: request without cookie → `{"error":"Unauthorized"}` + 401
5. Test 400: `{"inquiry_text": "short"}` → 400
6. Test 200: real inquiry (e.g. "Potrzebuję stronę internetową dla mojej kawiarni: strona główna, menu, galeria, formularz kontaktowy. Oczekuję nowoczesnego designu i wersji mobilnej.") → 200 + items
7. Test 422: nonsense brief ("asdfjkl asdfjkl") → 422 + `{"error":"inquiry_too_short"}`
8. Inspect items quality: do task names make sense? Are hours and rates in expected ranges?

## Performance Considerations

Haiku at ~1-2s p50 latency is acceptable for a scaffold call that S-01 will invoke once per session. No caching, no streaming. If latency becomes a UX concern in S-01, the endpoint contract is unchanged — only the model string and max_tokens change.

## Parked: User-Editable Prompt Context

The user identified a future need: allow users to configure their domain context (e.g. "I'm a graphic designer" vs "I'm a web developer") so rate anchors and task decomposition reflect their actual trade. This is explicitly out of scope for F-02. Candidate future slice: `user-prompt-context` — a settings field stored in a `profiles` table, injected into `SYSTEM_PROMPT` as a preamble at call time.
